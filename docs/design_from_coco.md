### 3.1 Current Model (What Exists)

```
                  ┌─────────────┐
```

**Entities:** Supplier, Part, Plant, OrderLine, Customer, Inventory (6 entities, matching the brief).

**Layering:**
- **RAW:** Source tables as-is (ERP, logistics, warehouse, contracts).
- **CURATED:** Dimension views + canonical fact dynamic tables + thin wrapper views.
- **ONTOLOGY:** Metadata tables + semantic view + Cortex Search.
- **GOVERNANCE:** Tags, masking policies, tests, alerts.
- **APP:** Cortex Agent + Streamlit.

### 3.2 Assessment

The data model is well-designed for the hackathon scope:

- **Referential integrity** is guaranteed by construction (ID arithmetic with `MOD` and `LPAD`). The orphan check in `01_synthetic_data.sql` validates this.
- **Star schema** with OrderLine as the central fact and dimensions radiating outward is appropriate for analytical queries.
- **Inventory** is correctly modeled as a separate fact (snapshot-based, different grain than order lines).
- **Contract documents** serve the unstructured search use case and connect back to suppliers.

### 3.3 Recommendations

| # | Change | Rationale |
|---|---|---|
| 1 | Keep as-is | The star schema is appropriate and well-executed. |
| 2 | Consider adding a `CURATED.DIM_CARRIER` | The `carrier` dimension on OrderLine has 5 values but no dimension table. Minor improvement for enrichment. |
| 3 | Consider a `CURATED.FACT_DAILY_AGGREGATE` | Pre-aggregated daily metrics would speed up time-series queries, but is not needed at 20K row scale. |

## 4. Supply-Chain Ontology and Relationships

### 4.1 Current Ontology (ONT_ENTITY + ONT_RELATIONSHIP)

Six entities, seven relationships:

```
OrderLine ──SOURCED_FROM──> Supplier (M:1 via supplier_id)
OrderLine ──CONTAINS──────> Part     (M:1 via part_id)
OrderLine ──SHIPPED_FROM──> Plant    (M:1 via plant_id)
OrderLine ──DELIVERED_TO──> Customer (M:1 via customer_id)
Inventory ──STOCKS────────> Part     (M:1 via part_id)
Inventory ──HELD_AT───────> Plant    (M:1 via plant_id)
Supplier  ──SUPPLIES──────> Part     (1:M via primary_supplier_id)
```

### 4.2 Assessment

The ontology is **correct and complete** for the six-entity scope. The `Supplier SUPPLIES Part` relationship correctly captures that each part has a primary supplier (from `RAW.PARTS.primary_supplier_id`), though this relationship is metadata-only and is not materialized in the semantic view (the semantic view correctly joins OrderLine->Supplier via `supplier_id` on the fact table, which reflects the actual supplier per order).

### 4.3 Recommendation

Keep as-is. The ontology metadata tables serve a dual purpose:
1. Self-documenting the domain model (displayed in the Streamlit "Ontology" tab).
2. Providing a reference for the agent's guardrail instructions.

## 5. Canonical Metric Definitions and Lineage

### 5.1 Metric Definitions (from ONT_METRIC → DT_ORDER_LINE → Semantic View)

| Metric | Canonical Definition | Formula | Governance |
|---|---|---|---|
| **OTD %** | Delivered (carrier POD) on or before date promised to customer | `100 * AVG(is_on_time)` | Shared; internal |
| **Fill rate %** | Qty shipped / qty ordered | `100 * SUM(qty_shipped) / NULLIF(SUM(qty_ordered), 0)` | Planning; internal |
| **In-full %** | Share of lines shipped in full | `100 * AVG(is_in_full)` | Planning; internal |
| **Days of inventory** | On-hand qty / avg daily usage | `SUM(on_hand_qty) / NULLIF(SUM(avg_daily_usage), 0)` | Planning; internal |
| **Landed cost/unit** | (line value + freight + duty) / units shipped | `SUM(landed_cost) / NULLIF(SUM(qty_shipped), 0)` | Procurement+Logistics; **restricted** |
| **Avg days late** | Avg days past promised date (late lines only) | `SUM(days_late) / NULLIF(SUM(1 - is_on_time), 0)` | Logistics; internal |

**Additional metrics in semantic view but not in ONT_METRIC:**
- `line_count`: `COUNT(order_line_key)` — utility metric, not a KPI.
- `total_landed_cost`: `SUM(landed_cost)` — aggregate version of landed cost.

### 5.2 Lineage

```
RAW.ERP_ORDER_LINES ──┐
                       ├──JOIN──> DT_ORDER_LINE ──> FACT_ORDER_LINE ──> SV_SUPPLY_CHAIN
RAW.LOGISTICS_SHIPMENTS┘                                                     │
                                                                    ┌────────┴────────┐
RAW.INVENTORY_SNAPSHOTS ──> DT_INVENTORY_LATEST ──> FACT_INVENTORY ─┘        │
                                                                    Cortex Agent
RAW.SUPPLIERS ──> DIM_SUPPLIER ──────────────────────────────────── (tool: Analyst)
RAW.PARTS ──> DIM_PART ─────────────────────────────────────────────┘
RAW.PLANTS ──> DIM_PLANT ──────────────────────────────────────────┘
RAW.CUSTOMERS ──> DIM_CUSTOMER ────────────────────────────────────┘

RAW.CONTRACT_DOCS ──> Cortex Search (CONTRACT_SEARCH) ──> Cortex Agent (tool: Search)
```

### 5.3 Consistency

Metric definitions are **consistent across all layers**:
- `ONT_METRIC.formula_sql` matches `DT_ORDER_LINE` column definitions matches semantic view `METRICS` formulas.
- The semantic view adds `NULLIF` guards that the `ONT_METRIC` table omits — this is correct (the semantic view is the executable layer; the ontology table is documentation).
- The consistency test procedure (`RUN_CONSISTENCY_TESTS`) independently computes golden values from `DT_ORDER_LINE` and compares against semantic view output. This closes the loop.

## 6. Governed Conversational Workflow

### 6.1 Current Design

```
User question (natural language)
        │
        ▼
  ┌─────────────────────────┐
  │   Cortex Agent          │
  │   (SUPPLY_CHAIN_AGENT)  │
  │                         │
  │  Orchestration logic:   │
  │  - Numbers → Analyst    │
  │  - Contracts → Search   │
  │  - Cross-domain → both  │
  └──────┬────────┬─────────┘
         │        │
    ┌────▼───┐  ┌─▼──────────┐
    │Analyst │  │Search      │
    │(SV)    │  │(Contracts) │
    └────┬───┘  └────┬───────┘
         │           │
    ┌────▼───┐  ┌────▼───────┐
    │Semantic│  │Cortex      │
    │View    │  │Search Svc  │
    │  ↓     │  │  ↓         │
    │Governed│  │CONTRACT_   │
    │SQL     │  │DOCS        │
    └────────┘  └────────────┘
         │           │
         ▼           ▼
    Governed answer with citations
```

### 6.2 How the Semantic View and Cortex Agent Work Together

1. **Semantic View** (`SV_SUPPLY_CHAIN`) defines the business vocabulary: entities, relationships, dimensions, facts, and metrics with human-readable synonyms and comments. Cortex Analyst uses this to translate natural language into SQL without relying on column names or table structures.

2. **Cortex Agent** (`SUPPLY_CHAIN_AGENT`) orchestrates:
   - Routes numeric/quantitative questions to the `SupplyChainAnalyst` tool (Cortex Analyst backed by the semantic view).
   - Routes contract/SLA questions to the `ContractSearch` tool (Cortex Search over contract docs).
   - For cross-domain questions (e.g., "late suppliers with expiring contracts"), calls Analyst first to identify suppliers, then Search for contract details.

3. **Governance enforcement:**
   - Masking policies on `FACT_ORDER_LINE.unit_cost`, `line_value`, `landed_cost` mean the semantic view returns NULLs for unauthorized roles — the agent sees NULLs and explains the restriction.
   - The agent's instructions include a guardrail: if a metric is not defined, it lists the 6 canonical metrics and asks the user to clarify.

### 6.3 Assessment

This is a strong design. The separation of concerns is clean:
- Semantic view = business vocabulary + metric definitions.
- Agent = orchestration logic + user-facing behavior.
- Masking policies = data governance at the platform level.
- Consistency tests = trust verification.

### 6.4 Recommendations

| # | Change | Rationale |
|---|---|---|
| 1 | Add **verified queries** (VQRs) to the semantic view | VQRs improve Analyst accuracy for common questions. Add 3-5 verified queries for the sample questions in the Streamlit app. |
| 2 | Add **`AI_SQL_GENERATION`** instructions to the semantic view | Custom SQL generation hints (e.g., "always filter to the last 180 days unless the user specifies a date range") improve query quality. |
| 3 | Add **`code_execution`** tool to the agent | Enables the agent to run Python for more complex analytical questions (e.g., trend detection). Low effort, high demo value. |
| 4 | Add **`data_to_chart`** tool to the agent | Enables chart generation in CoWork/Snowsight. Good demo moment. |
| 5 | Consider **analytical search** on the Search tool | Extends beyond simple RAG retrieval to allow aggregate queries over the document corpus (e.g., "how many suppliers have SLA below 92%?"). |

## 8. Risk Assessment

### 8.1 Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Cortex Analyst generates incorrect SQL | Medium | High | Add verified queries (VQRs) for common questions. The consistency test procedure validates metric correctness. |
| LLM model deprecation during hackathon | Low | High | `orchestration: auto` handles this; cross-region is already enabled. |
| Dynamic table refresh failure | Low | Medium | XS warehouse may occasionally queue behind other workloads. Monitor with `SHOW DYNAMIC TABLES`. |
| `SEARCH_PREVIEW` function deprecation | Low | Medium | The Streamlit app uses this function directly. Check if it's been superseded. |
| Streamlit `_snowflake` API only works in Snowsight | Known | Medium | The "Ask" and "Personas" tabs error outside Snowsight. The app handles this with try/except, but it limits local development. |

### 8.2 Data Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Synthetic data doesn't exhibit enough variation in metrics | Medium | Medium | The `sup_bias` mechanism creates systematic supplier lateness, but OTD may cluster around 50-60%. Run and inspect actual values. |
| `avg_days_late` division by zero | Low | Low | Semantic view uses NULLIF. Only triggers if every single order line is on-time (extremely unlikely with the bias mechanism). |
| Inventory DOI unrealistic values | Medium | Low | Random `on_hand_qty` (0-4000) and `avg_daily_usage` (5-120) may produce extreme ratios. Review after deployment. |

### 8.3 Governance Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Masking policies evaluated on wrong role | Low | High | Agent calls use the querying user's **default role**, not the session role. The user `MANASAD` has default role `ACCOUNTADMIN`, which bypasses masking. For the persona demo to work, you must switch roles. |
| `IS_ROLE_IN_SESSION` vs agent context | Medium | High | When the agent calls Analyst, the SQL executes under the caller's default role. If the default role is ACCOUNTADMIN, masking won't apply even for the persona demo. Test this carefully. |
| Tags not enforced | Known | Low | Tags (`METRIC_OWNER`, `DATA_SENSITIVITY`) are informational metadata, not access controls. This is fine for a demo. |

### 8.4 Implementation Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `STREAMLIT_STAGE` not explicitly created | Low | Low | `snow streamlit deploy` typically creates it. If not, add `CREATE STAGE IF NOT EXISTS APP.STREAMLIT_STAGE` to `00_setup.sql`. |
| `deploy.sh` assumes bash on Linux/Mac | Medium | Low | You're on Windows. Use `snow sql -f` commands manually or write a PowerShell equivalent. |
| `persona_consistency.py` requires `snowflake-connector-python` | Low | Low | Not installed by default in SiS. This test is meant for CLI only. |
| `CORTEX_AGENT_USER` database role not granted | Medium | Medium | `00_setup.sql` grants `SNOWFLAKE.CORTEX_USER` but the docs recommend `SNOWFLAKE.CORTEX_AGENT_USER` for agent access. Both may work since `CORTEX_USER` is granted to PUBLIC by default in most accounts. |

```sql
AI_VERIFIED_QUERIES (
  otd_by_region AS (

  ),
  worst_suppliers AS (
    QUESTION 'Which 5 suppliers have the lowest on-time delivery?'
    SQL 'SELECT supplier_name, otd_pct, line_count FROM SEMANTIC_VIEW(SC_ONTOLOGY.ONTOLOGY.SV_SUPPLY_CHAIN DIMENSIONS suppliers.supplier_name METRICS order_lines.otd_pct, order_lines.line_count) ORDER BY otd_pct ASC LIMIT 5'
  ),
  doi_by_category AS (
    QUESTION 'What is days of inventory by part category?'
    SQL 'SELECT part_category, days_of_inventory FROM SEMANTIC_VIEW(SC_ONTOLOGY.ONTOLOGY.SV_SUPPLY_CHAIN DIMENSIONS parts.part_category METRICS inventory.days_of_inventory) ORDER BY days_of_inventory DESC'
  ),
  overall_otd AS (
    QUESTION 'What is our overall on-time delivery rate?'
    SQL 'SELECT otd_pct FROM SEMANTIC_VIEW(SC_ONTOLOGY.ONTOLOGY.SV_SUPPLY_CHAIN METRICS order_lines.otd_pct)'
  ),
  landed_cost_by_country AS (
    QUESTION 'What is the average landed cost per unit by supplier country?'

  )
)
```
